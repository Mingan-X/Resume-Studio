# 进程启动与Qdrant超时排查

历史诊断快照；后续T7实现与验证结果见[开发进度](../progress.md)，下文“当前”均指诊断当时。

日期：2026-11-25。范围：S1.3验收遗留的原因分析与修复方案；没有修改业务源码、测试断言、服务配置或正式超时。实验脚本及原始计时保存在被忽略的 `data/failure-diagnosis/`，仅使用合成数据。

## 结论与确定程度

1. **进程启动的主要耗时位于模块加载。** 当前API/Worker静态导入bootstrap，再在入口主体中校验配置；bootstrap同时导入API与Worker模块。缺配置也会先加载Nest、RxJS、健康检查等约648个模块。测试负载下测到9.369秒才返回CONFIG_INVALID，其中CPU约0.781秒，足以接近10秒启动失败测试上限并超过8秒ready等待。现有失败日志未保留分段计时，不能断言每次失败都完全由同一环节造成。
2. **Qdrant主要瓶颈在当前持久化存储路径。** 客户端耗时与服务端处理时间接近；相同镜像在现有卷创建集合需2.9–6.5秒，隔离tmpfs中约3.6–3.8毫秒。项目、pnpm store和Docker虚拟磁盘都位于E盘SATA机械硬盘，Linux I/O压力明显。证据支持存储延迟，尚未进一步区分物理磁盘寻道、Windows分页、VHD/文件系统同步或其他进程I/O的占比。
3. **清理窗口是确定的测试逻辑缺口。** `infrastructure.test.ts`在create超时后只查询一次exists，false并不能证明服务端不会迟到创建；之前三次5秒超时后创建成功的日志已证实这一窗口。仅修改启动顺序或串行执行不能修复它。

上述为排查结论，不代表修复已经交付或S1.3验收通过。

## 现场与对照实验

### 环境

- Node24.22.3；Windows；Docker6CPU、约5.8GiB内存；项目 `E:\Resume-Studio\Resume-Studio-Backend`。
- E/D盘同属 `ST1000LM035-1RK172` SATA机械硬盘；C盘为 `SAMSUNG MZVLB256HBHQ-000L2` NVMe。
- Docker设置 `CustomWslDistroDir` 为 `E:\DockerData\wsl\DockerDesktopWSL`，实际数据盘 `disk/docker_data.vhdx` 约22.2GB；pnpm store为 `E:\.pnpm-store`。
- 抽样Windows可用内存约2.1GiB，PagesInputPersec约26500；Linux I/O pressure full avg10约23%–41%。这些是现场抽样，不能证明某个特定进程或杀毒软件是根因。
- C盘剩余约20.0GB，小于现有Docker数据VHD文件约22.2GB；当前不能直接迁入，还需额外运行空间。

### 进程启动

通过Node预加载脚本与同步模块钩子计时，只记录模块路径和时间，不打印环境变量或配置值。

| 场景 | 实测 |
|---|---|
| 原API入口，缺配置，独立运行 | 1.531秒，648个模块；随后无钩子运行0.608秒 |
| 原Worker入口，缺配置 | 同样648个模块；约0.54–0.58秒 |
| 原API入口，与HTTP/观测测试同时加载 | 9.369秒，648个模块，CPU0.781秒；最终CONFIG_INVALID |
| 临时“先校验配置”原型，独立运行 | 1.506秒，97个模块，CPU0.156秒 |
| 同一原型，与上述测试同负载 | 0.144秒，97个模块，CPU0.094秒；最终CONFIG_INVALID |
| 有效配置分段计时 | 配置模块73ms、bootstrap导入403ms、创建API222ms、listen22ms、close1ms；Worker上下文创建2ms |

模块加载样本中，单个Zod文件曾耗660ms，RxJS文件曾耗394ms；缓存与磁盘状态会改变结果。原型减少加载范围具有明确代码依据，但0.144秒是已加载过文件后的样本，不能据此承诺冷启动也固定达到该值。有效配置的分段计时未发现监听端口或Nest初始化本身耗8秒的证据。

### Qdrant

先核对本项目容器标签、端口及卷归属。对每轮随机名称记录manifest，再创建/查询/删除，删除前再次核对归属。本次诊断请求使用15秒观测窗口，以拿到服务端实际处理时间；**正式客户端和测试仍为5秒**，不将诊断成功算成正式测试通过。

## 建议的解决方案与验收

| 优先级 | 修改范围 | 方案 | 验收方式 |
|---|---|---|---|
| P1 | API/Worker入口及生命周期模块 | 配置校验前只加载最小配置/安全错误报告；校验通过后动态加载对应bootstrap。拆分API/Worker装配，避免空Worker加载API链路。错误报告函数也必须保持无Nest运行依赖，否则会再次触发整棵导入树 | 原缺配置/非法配置/日志脱敏测试不变；对冷/暖启动分别计时，确认失败路径不加载Nest；有效API/Worker启动及关闭保持原语义 |
| P1 | Qdrant测试资源清理 | 将“创建结果未知”作为显式状态；使用本轮UUID/manifest，等待有界完成或持久化待清理信息，归属校验后精确删除。一次exists=false不能结束未知创建的清理；清理超时必须保留manifest并明确失败 | 用可控延迟服务验证“客户端超时→第一次exists=false→迟到创建→最终清理”；真实Qdrant验证本轮资源不残留，不批量删前缀 |
| P1 | 本机持久化存储 | 将项目/依赖缓存和Docker数据盘迁至容量足够的SSD/NVMe，分开评估及实施。先准备空间与备份，再使用受控迁移，逐项核对旧卷、凭证、Checkpoint与Langfuse数据 | 原5秒诊断和8/10秒启动限制下验证冷启动与重复运行；记录分位耗时、无失败和精确清理；实测前不能保证SSD方案达到具体数值 |
| P2 | 诊断配置/性能策略 | 区分小规模健康/CRUD诊断与集合创建性能目标；若实际支持机械盘，应另设明确的管理操作预算，并基于实测审批，同时保留故障边界测试 | 不能只把统一5秒改大来过关；区分SLO、单次超时、总预算和超时后对账 |

最先可实施的是入口最小化与清理窗口修复。SSD迁移涉及环境和其他Docker数据，当前未执行；C盘空间不足，不能擅自搬迁。串行执行、warm-up或关闭Langfuse可作为定位手段，不能替代根因修复；不建议关闭安全软件或将真实持久化卷改为tmpfs。

本轮没有修改正式实现或断言，没有重新宣称基础/集成全部通过。建议以上修复按S1.3验收遗留单独拆分并记录，完成后再运行原验收检查。
