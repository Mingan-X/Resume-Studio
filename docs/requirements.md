# 业务需求

版本：0.1；日期：2026-11-23。本文定义目标行为，**不是已经实现的功能清单**。

当前已实现工程基础、任务可靠性、简历文件/文本证据与岗位草稿/发布HTTP；语义简历抽取、真实索引、画像/匹配及报告仍待后续阶段。正式Rubric v1已导入但待维护者审核，兼容模型适配器只通过本地HTTP桩验证。阶段状态见[进度](progress.md)，既定决策见[路线图§6](development-roadmap.md#6-待决策事项)。

## 1. 用户与范围

首版服务求职者：上传自己的简历，查看证据化画像、适合进一步了解的岗位及差距。岗位来源先采用人工提供或合成 JD，不接招聘平台爬虫，不自动投递。

开发期间默认本机单用户，仍在数据模型中保留 ownerId，禁止读取他人的任务/文件。面向网络发布前补齐登录、权限和用户数据删除；单用户开发模式不能直接作为公网部署方案。

## 2. 六维定义

| 维度 | 看什么证据 | 不应推断什么 |
|---|---|---|
| 技术深度 | 具体技术问题、方案选择、权衡与个人职责 | 技术名词数量等于深度 |
| 工程能力 | 测试、交付、质量、可维护性、稳定性实践 | 写“熟悉工程化”即高等级 |
| 业务理解 | 业务目标、需求取舍、指标及产品约束 | 公司名气等于业务能力 |
| 项目影响力 | 个人贡献、影响范围、可核对的结果与基线 | 团队全部成果归于个人 |
| 协作沟通 | 跨角色协作、推动落地、文档与反馈 | 没写沟通经历即不善沟通 |
| 成长性 | 新技能应用、责任变化、反馈后的改进 | 依据年龄、性别等无关属性推断潜力 |

采用独立版本的 rubric；借鉴参考项目 L1–L5 的思想，但首版等级定义、映射分值与权重需审查。评估的是文本中能支持的能力证据。

## 3. 证据与评分语义

- 引用必须指向本次输入版本的文本块和字符区间，quote 必须与区间一致。PDF 可有页码/坐标；DOCX 用段落或抽取块编号，不虚构页码。
- 语义判断不等于数学计算：模型选择判定并解释证据，代码按已批准规则计算分数。模型返回额外的综合分字段应被 Schema 拒绝。
- `unknown` 表示资料未充分覆盖；`unmet` 表示有足够依据认为不满足。二者必须分别展示。
- 推荐默认采用证据支持的保守分数；unknown 的数值贡献可为 0，但语义标签仍为 unknown，同时显示覆盖率与上界。不能通过跳过 unknown 的分母抬高分数。
- 显式硬条件未满足的岗位不进入推荐榜；硬条件无法验证的岗位进入“待核实”集合。软技能不自动升级成硬淘汰门槛。
- 岗位综合分根据该岗位的逐条要求计算，不直接将候选人的六维画像总分当作岗位匹配度。
- 六维画像只能作为辅助上下文，不能仅凭画像的L1–L5等级直接推导某条岗位要求的met/partial/unmet；逐项判断必须对应该要求与简历证据，信息不足仍是unknown。
- 权重输入必须是有限非负数，参与计算的总权重必须大于0；按Schema拒绝缺失的必需权重、重复维度/要求ID、负数、NaN、Infinity和不支持的维度，不能静默补默认值。分维归一化时各有效维度内的要求权重总和也必须大于0；单项0仅表示不计分，不跳过要求判断或硬门槛。发布和调权重算都执行这些校验。
- 改权重重算复用同一批已持久化判断，模型调用数为 0。重算只能保证在原候选集中排序；重新召回属于新分析。
- 只有“固定结构化判断 + 固定输入快照 + 固定评分规则”的计算可保证一致；对 LLM 重新分析，即使 temperature=0，也不承诺逐字或数值完全相同。
- 报告快照须关联resumeVersionId及输入配置快照、冻结的CandidateSet与jobVersionId、ProfileAssessment、rubricVersion、scoringPolicyVersion及权重快照，并完整覆盖全部计划要求及各自的执行状态。已完成判断的要求关联相应RequirementJudgment结果；未执行、执行失败或预算截断而未完成的要求保留未完成状态与原因，不伪造RequirementJudgment，也不将其当作unknown判断结果。这里约束报告可追溯的内容，不预先限定这些信息是否使用同表、分表或其他持久化结构。派生重算报告关联原报告，不覆盖原判断、执行状态快照和历史报告。

任务恢复/重试与重新分析是不同操作：恢复和重试保留原任务身份、冻结输入及幂等产物，并遵守执行租约/fence隔离；旧执行已确认停止才可复用原Checkpoint thread，否则创建新恢复thread并拒绝旧执行迟到业务写入，taskId仍不变。重新分析或重新召回创建新的AnalysisTask/taskId，保留历史任务和报告。JD索引使用独立JobIndexTask，和分析共享Outbox/消息/租约基础设施，但保持独立业务状态；新索引输入/目标版本建新索引任务，原版本失败重试不换任务身份。S1.4已验证合成任务执行/恢复，S2.2岗位发布已事务创建真实JobIndexTask及Outbox；真实索引执行与简历分析业务图仍待S2.3/S2.4。

公式、边界处理和示例见[架构 §8](architecture.md#8-评分引擎设计)。

## 4. 文件解析范围与失败体验

首版默认范围为带文本层的PDF与正文/表格含文本的DOCX，**不承诺扫描PDF的OCR**。扫描PDF、复杂图文排版、加密文件、损坏ZIP、空文本应返回具体原因，不输出虚假的成功画像。OCR是否纳入MVP须根据质量实验、成本和隐私要求单独确认；即使引入，也保持Node/TypeScript后端，通过JS组件或外部服务适配，不新增Python服务。

PDF.js 提取文字并不自动解决多栏阅读顺序；Mammoth 提取纯文本并不保证原始版面或页码。进入解析阶段必须以中文、双栏、表格、项目列表样本做质量实验，再确定坐标/段落映射方案。

解析安全边界要求：除上传大小/签名外，DOCX/ZIP需限制解压后总大小、单条目大小、文件条目数和异常压缩比，拒绝嵌套/损坏/异常压缩结构；禁止绝对路径、`..`路径穿越、符号链接或其他会写出受控目录的条目。PDF/DOCX均须限制页数/文本量、CPU、内存和解析总耗时，限制外部引用与网络访问；无法安全处理时明确失败，不无限递归或无界解压。具体阈值通过恶意及复杂样本实验后配置，S2.1已在本机Windows以合成样本验证相应预检和受限子进程，资源边界与未验证平台见[文件证据说明](resume-evidence.md)及进度，不能推广为任意文件的安全或质量保证。

## 5. 建议规模与预算（目标，不是实测）

- 评测数据仅采用合成或经过授权且脱敏的数据。首批JD目标100–300条，简历至少20份；实际样本来源/授权需确认，脱敏不能代替授权。
- 默认关键词召回50、向量召回50，去重融合后选最多20个岗位精判；**400条requirement judgment是单次分析的默认预算上限**，不因任务重试重新获得一份预算。按jobVersionId/requirementId统计已完成唯一判断，模型重试另计调用/token/费用预算。超过上限返回明确的截断状态、计划数/已完成数/未完成数量及原因；未执行的要求不冒充已有判断或悄悄删除，报告标为PARTIAL并说明排名覆盖范围。该上限为待实测的初始配置，不是生产容量保证。
- Worker 初始同时运行 1 个分析，岗位匹配并发 3；后续通过测量调整。
- 创建任务接口目标 p95 <1 秒；单次分析目标 <10 分钟，前提是明确的样本规模和模型服务可用性；初期没有达标数据。
- 任务状态建议每 2 秒轮询；后续 SSE 复用持久化事件，网络断线后可补读。
- API/Worker 重启、RabbitMQ 重连、重复投递不得丢失已提交任务或重复提交最终报告。

上述并发数、轮询间隔、预算和时延均为设计起点或目标，尚未通过真实业务数据、模型或生产负载验证。

## 6. 不在第一版范围

通用 Supervisor、多智能体自由会话、任意 SQL/文件执行工具、MCP 平台、自动岗位抓取、自动投递、微服务拆分、跨地域高可用、未经授权的真实数据集。

前端采用 Vue 3 + TypeScript，位于独立仓库 Resume-Studio-Frontend，通过[接口契约规范](api-contract.md)约定的HTTP与进度接口获取数据。报告展示包含六维画像、证据展开、候选差距、排名与任务错误，不显示“模型正在思考”的伪进度。前端页面与交互需求见[前端产品与界面规范](https://github.com/Mingan-X/Resume-Studio-Frontend/blob/main/docs/ui-guidelines.md)。
